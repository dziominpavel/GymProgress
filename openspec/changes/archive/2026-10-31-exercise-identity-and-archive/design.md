# Design

## Context

См. `proposal.md` — Why. Текущее состояние, важное для реализации:

- Room версии 6; `WorkoutEntry` хранит только `exerciseName`, `Exercise.name` имеет case-sensitive уникальный индекс. Связь записи с упражнением — текстовая.
- `WorkoutViewModel.deleteExercise` делает жёсткое удаление; `renameExercise` обновляет записи по точному совпадению старого имени.
- `WorkoutViewModel.safeDb` — единая обёртка ошибок; `allEntries` уже отдаётся в порядке `date ASC, id ASC`.
- SQLite `LOWER`/`COLLATE NOCASE` корректно работают только с ASCII, поэтому case-insensitive нормализация кириллицы должна вычисляться в Kotlin, а не SQL-запросом.
- `exportSchema = false`, `androidTest`-тестов и `room-testing` пока нет.
- `allExercises` используется и для выбора упражнений, и для сопоставления истории; просто отфильтровать архивных из общего списка нельзя — сломается история.

## Goals / Non-Goals

**Goals:**

- Одна миграция 6 → 7: стабильные `clientId`, `exerciseId` с FK, `nameKey`, `isArchived`; существующие данные не теряются.
- Архивирование вместо удаления по умолчанию; восстановление и окончательное удаление с сохранением истории.
- Единая нормализация имён и защита от дубликатов на уровне приложения и БД.
- Переименование и слияние дубликатов обновляют денормализованное `exerciseName` в записях.
- Подготовить фундамент для следующего change `backup-export-import`.

**Non-Goals:**

- Экспорт/импорт JSON и CSV — отдельный change.
- Полный перевод скоринга, тренера и всего UI на `exerciseId`; допускается имя как денормализованный ключ отображения.
- Облачная синхронизация и разрешение конфликтов между устройствами.
- Изменение формата даты и порядка сортировки.

## Decisions

### 1. Схема данных

`Exercise`:

- `clientId: String` — UUID v4, `NOT NULL`, уникальный индекс.
- `nameKey: String` — результат `FormatUtils.normalizeExerciseNameKey(name)`, `NOT NULL`, уникальный индекс.
- `isArchived: Boolean = false`.
- Уникальный индекс по `name` удаляется; отображаемое имя может отличаться, но `nameKey` — нет.

`WorkoutEntry`:

- `clientId: String` — UUID v4, `NOT NULL`, уникальный индекс.
- `exerciseId: Long?` — nullable, индекс, FK на `Exercise.id` с `ON DELETE SET NULL`.
- `exerciseName: String` остаётся `NOT NULL` как денормализованный кэш отображения и fallback для «сиротских» записей.

Почему `nameKey`, а не `COLLATE NOCASE`: SQLite не умеет Unicode case folding для кириллицы. `nameKey` считается в Kotlin тем же кодом, что и текущая UI-проверка, и хранится в БД. Уникальный индекс по `nameKey` закрывает race conditions.

Почему `exerciseId` nullable: после окончательного удаления упражнения и для legacy-записей без пары связь отсутствует, но запись должна остаться читаемой.

### 2. Миграция 6 → 7

`MIGRATION_6_7` выполняется в одной транзакции Room:

1. Добавить nullable-колонки `exercises.clientId`, `exercises.nameKey`, `exercises.isArchived`, `workout_entries.clientId`, `workout_entries.exerciseId`.
2. Прочитать упражнения в Kotlin, вычислить `nameKey`, сгенерировать `clientId`, обновить строки.
3. Сгруппировать упражнения по `nameKey`; каноническим считать упражнение с наибольшим числом записей, при равенстве — с меньшим `id`. Для каждой записи вычислить `nameKey` и проставить `exerciseId` канонического упражнения; `exerciseName` заменить на каноническое имя. Дубликаты упражнений удалить.
4. Сгенерировать `clientId` для записей.
5. Пересобрать таблицы, потому что SQLite не позволяет добавить FK и NOT NULL к существующей таблице:
   - создать `exercises_new` с новыми колонками и ограничениями, скопировать данные;
   - создать `workout_entries_new` с FK на `exercises_new`, скопировать данные;
   - удалить старые таблицы, переименовать новые, создать индексы.
6. Добавить `MIGRATION_6_7` в `addMigrations` и поднять версию БД до 7.

Почему нормализация в Kotlin внутри `Migration.migrate`: это единственный способ применить тот же Unicode-алгоритм, что и в приложении, без ICU-расширения SQLite. Миграция уже выполняется вне главного потока.

Почему пересборка таблиц: `ALTER TABLE` в SQLite не добавляет внешний ключ и не меняет ограничения. Пересборка — стандартный путь Room; порядок «создать обе новые таблицы → скопировать → удалить старые → переименовать» сохраняет FK-ссылки.

Альтернатива — оставить только app-level проверки и не делать FK. Отклонено: цель change — целостность на уровне БД, а не только UI.

### 3. Идентификаторы

`clientId` генерируется через `UUID.randomUUID().toString()`:

- в конструкторе сущности как значение по умолчанию — для новых строк;
- в миграции — для существующих.

`clientId` не меняется при переименовании, архивировании, восстановлении и редактировании записи. Это контракт для будущего merge при импорте.

### 4. Жизненный цикл упражнения

- «В архив»: `isArchived = true`. Данные и связи не меняются.
- «Восстановить»: `isArchived = false`.
- «Удалить навсегда»: физическое удаление; FK `ON DELETE SET NULL` очищает `exerciseId` у записей, `exerciseName` остаётся.
- Диалог удаления по умолчанию предлагает архив; окончательное удаление — вторичное действие с предупреждением, что история сохранится.

Архивные упражнения:

- не попадают в список выбора `AddEntryDialog`, в рекомендации тренера и в быстрый выбор;
- остаются в `allExercises` для статистики, истории и сопоставления старых записей;
- в списке статистики помечаются как «(архив)».

### 5. Переименование и слияние

`updateExercise` в одной транзакции:

1. Проверяет `nameKey` нового имени.
2. Обновляет `Exercise.name` и `nameKey`.
3. Вызывает `WorkoutDao.updateExerciseNameForEntries(exerciseId, newName)` для связанных записей.

При миграции дубликатов записи получают каноническое имя, поэтому существующие калькуляторы, которые сравнивают `exerciseName`, продолжают работать без переписывания.

### 6. Точки интеграции

- `ExerciseDao`: `getAllExercises()` (включая архив), `getActiveExercises()`, `countByNameKey`, архивирование/восстановление через `@Update`.
- `WorkoutDao`: `getEntriesByExerciseId`, `updateExerciseNameForEntries`, `countEntriesByExerciseId`; `getEntriesByExercise` остаётся для legacy-fallback.
- `WorkoutViewModel`: `addExercise`/`updateExercise` считают `nameKey`; `archiveExercise`, `restoreExercise`, `deleteExercisePermanently`; `addEntry` резолвит `exerciseId` и блокирует архивное упражнение; `entriesForSelectedExercise` сначала фильтрует по `exerciseId`, затем по нормализованному имени.
- `MainActivity`: новые колбэки для архива/восстановления/окончательного удаления; группировка PR по `exerciseId` с fallback на `nameKey`.
- `ExercisesScreen`: переключатель «Архив», действия карточек, обновлённый диалог удаления.
- `AddEntryDialog`: фильтр `!isArchived`; `EditEntryDialog` ищет `isBodyweight` по `exerciseId`.
- `StatsScreen`, `JournalScreen`, `WorkoutHistoryScreen`: отображение по денормализованному `exerciseName`; выбор упражнения в статистике сохраняет архивные с пометкой.
- `TrainerRecommendationEngine`: архивные исключаются из кандидатов, но остаются доступны для разбора истории.

### 7. Тестирование

- Unit: `normalizeExerciseNameKey` для кириллицы, NBSP, повторяющихся пробелов; вычисление `nameKey`; чистая функция выбора канонического дубликата.
- `androidTest`: `MigrationTestHelper` на схеме версии 6 с фикстурами (дубликаты, кириллица в разном регистре, NBSP, запись без пары, bodyweight). Проверить: количество записей не изменилось, `clientId` уникальны, `nameKey` уникальны, `exerciseId` проставлен, «сирота» осталась с `NULL`, FK `SET NULL` работает, `nameKey` совпадает с Kotlin-нормализацией.
- UI/ручное: архив скрывает упражнение из выбора и тренера, но не из истории/статистики; восстановление возвращает; переименование обновляет историю; окончательное удаление сохраняет записи; повтор архивной записи блокируется.
- Сборка: `assembleDebug`, `testDebugUnitTest`, `lintDebug`; `connectedDebugAndroidTest` — при наличии устройства.

Для тестов миграции включить `exportSchema = true` и добавить `room-testing` в `androidTestImplementation`.

## Risks / Trade-offs

- **Потеря данных при слиянии дубликатов** → каноническое упражнение выбирается по числу записей; количество записей проверяется тестом; миграция атомарна.
- **Ошибка Unicode-нормализации** → нормализация выполняется тем же Kotlin-кодом, что и в UI; тест на кириллицу и NBSP.
- **Пересборка таблиц с FK** → тест миграции на реальной схеме; проверка Room schema validation после открытия БД.
- **Старые версии приложения не откроют БД версии 7** → это осознанное breaking-изменение; выпускать только с новой версией, не откатывать APK после обновления.
- **Архивные упражнения остаются в старых путях** → фильтровать в точках выбора, а не в `allExercises`; тесты на повтор записи и рекомендации.
- **Денормализованное имя может разойтись с упражнением** → переименование и слияние обновляют `exerciseName` в той же транзакции; `exerciseId` остаётся источником истины.
- **Производительность миграции** → один проход по упражнениям и записям, карты в памяти; для 10 000 записей это допустимо.

## Migration Plan

1. Добавить поля и индексы в сущности, включить экспорт схемы.
2. Реализовать `MIGRATION_6_7` и тест миграции на фикстурах версии 6.
3. Обновить DAO и `WorkoutViewModel`; затем UI справочника и точек выбора.
4. Прогнать unit-тесты, migration-тест, `lintDebug`, ручной сценарий обновления с реальным дампом БД.
5. Выпустить в одном релизе; откат — только через восстановление резервной копии БД, обратной миграции нет.
