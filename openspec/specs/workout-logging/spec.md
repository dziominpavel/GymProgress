# workout-logging Specification

## Purpose

Записи журнала хранят стабильную ссылку на упражнение, поэтому переименование, архивирование и удаление упражнения не разрывают историю; записи без найденного упражнения остаются читаемыми.

## Requirements

### Requirement: Связь записи с упражнением

Каждая новая запись журнала SHALL быть связана с активным упражнением по `exerciseId`, если пользователь выбрал его из справочника. Для существующих записей связь SHALL быть восстановлена миграцией по нормализованному имени; при отсутствии пары `exerciseId` остаётся `NULL`.

#### Scenario: Новая запись получает exerciseId

- **WHEN** пользователь добавляет запись для упражнения из справочника
- **THEN** запись сохраняется с `exerciseId` этого упражнения

#### Scenario: Существующие записи связываются миграцией

- **WHEN** выполняется миграция БД версии 6
- **THEN** записи с совпадающим нормализованным именем получают `exerciseId`

#### Scenario: Запись без пары остаётся читаемой

- **WHEN** для записи нет упражнения в справочнике
- **THEN** `exerciseId` остаётся `null`, а запись доступна по сохранённому `exerciseName`

### Requirement: Архивное упражнение не принимает новые записи

Система MUST NOT создавать новые записи для архивного упражнения. При попытке добавить такую запись, например через «Повторить сегодня» из истории, система MUST показать сообщение и предложить восстановить упражнение.

#### Scenario: Повтор архивной записи

- **WHEN** пользователь пытается повторить запись архивного упражнения
- **THEN** новая запись не создаётся, показывается сообщение о необходимости восстановить упражнение

#### Scenario: Повтор после восстановления

- **WHEN** упражнение восстановлено из архива и пользователь повторяет запись
- **THEN** новая запись создаётся и связывается с этим упражнением

### Requirement: История архивного упражнения

Записи архивного упражнения MUST оставаться в журнале, истории и статистике. Отображение MUST использовать актуальное имя упражнения, если связь существует, иначе сохранённый `exerciseName`.

#### Scenario: Архивное упражнение в статистике

- **WHEN** пользователь открывает статистику архивного упражнения
- **THEN** график и записи доступны

#### Scenario: Отображение имени после переименования

- **WHEN** упражнение переименовано
- **THEN** связанные записи показывают новое имя

#### Scenario: Отображение имени без связи

- **WHEN** у записи нет `exerciseId`
- **THEN** запись показывает сохранённый `exerciseName`

### Requirement: История после окончательного удаления

После окончательного удаления упражнения записи журнала MUST сохраниться и отображаться по сохранённому имени. Система SHALL разрешать повтор такой записи, создавая новую запись с `exerciseId = NULL`.

#### Scenario: Записи удалённого упражнения видны

- **WHEN** упражнение удалено навсегда
- **THEN** его записи остаются в журнале и истории

#### Scenario: Повтор записи удалённого упражнения

- **WHEN** пользователь повторяет запись удалённого упражнения
- **THEN** создаётся новая запись с тем же `exerciseName` и `exerciseId = NULL`

### Requirement: Клиентский идентификатор записи

Каждая запись журнала SHALL иметь уникальный `clientId`, не меняющийся при редактировании. Для существующих записей `clientId` SHALL быть заполнен миграцией, для новых — при создании.

#### Scenario: Существующие записи получают clientId

- **WHEN** выполняется миграция БД версии 6
- **THEN** у каждой записи есть непустой уникальный `clientId`

#### Scenario: Редактирование не меняет clientId

- **WHEN** пользователь меняет вес, повторы или дату записи
- **THEN** `clientId` записи остаётся прежним

### Requirement: Сортировка записей

Списки записей MUST сохранять порядок `date ASC, id ASC` независимо от наличия `exerciseId`.

#### Scenario: Порядок не меняется

- **WHEN** записи отображаются в журнале, истории или диалогах
- **THEN** более ранние даты идут выше, а внутри одного дня записи идут по возрастанию `id`
